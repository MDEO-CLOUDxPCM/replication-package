# The msa feature model of the defects-fixed Kotlin MiSArch (`misarch-kotlin.m`)

`misarch-kotlin.m` is round 2's msa seed model: the pure-Kotlin MiSArch with the defects fixed (`misarch-kotlin`
`main`, e7f1a03 when the model was generated; fixes: `misarch-kotlin/docs/fixes/`). It is an imported input:
`../../extract/assemble.py` maps it to the domain model (`msaMapping`), and `../../generator/` reads its workload and
System parameters. It was generated by msa's `tools/gen_model.py --stack kotlin` (not in this package) from the same
tables as msa's model of the original MiSArch (`misarch.m`, not in this package); the comments at the top of
`misarch-kotlin.m` give the load factor, payment mix and calibration it was generated with.

Every one of the need rows of the original model was checked against the Kotlin code and carries Kotlin evidence in
`misarch-kotlin.m` (`<service> <path>:<line>`, with the path relative to
`misarch-kotlin/services/<service>/src/main/kotlin/org/misarch/<service>/`). Operations whose code or behaviour
differs from the original carry Kotlin evidence too; the others behave as in the original and keep its evidence.
Topic and sync-call numbers (T1–T35, S20–S27) are msa's numbering. Topic names, routes and Dapr app ids are the same
in Kotlin.

**Added (3 structural changes):**

1. **return holds a ProductVariantVersion copy** (`createReturn → ProductVariantVersion`, REPLICATION/REPLICA).
   `return event/EventController.kt:91` subscribes `catalog/product-variant-version/created` (T10). The
   original had the handler without `@Topic`, so every return failed. The return period is read in
   `service/ReturnService.kt:117`. T10 has 3 copy holders: order, shipment and return.
2. **Order compensation on a failed shipment creation** (T30): operation `createOrderCompensation`
   (REACTION, F17, writes OrderCompensation; `order event/EventHandlers.kt:86-97`) and the Buy step
   `createShipments → OrderCompensation` (COMMAND/ASYNC_EVENT, `callsPerOp` 0.001, assumed: shipment's
   provider registration has to fail 4 times, `shipment service/ShipmentService.kt:165,277-295`).
   order subscribes T30 (`order event/OrderEvents.kt:47`). It publishes T20, which has no
   subscriber and is not modelled.
3. **payment-enabled for PREPAYMENT comes from the provider callback.** Buy steps
   `updatePaymentStatus → Shipment (createShipments)` and `updatePaymentStatus → ProductItem
   (setInFulfillment)` (`payment provider/PaymentProcess.kt:197-207`). INVOICE and CREDIT_CARD
   publish at the start of the payment (`:141-143`). (The original MiSArch publishes at the same two points;
   `misarch.m` simplifies this to "at the start".)

**`callsPerOp` that differ** (from the code, the payment method mix and the provider stub's success rate
s = 0.95, `simulation config/SimulationVariables.kt:95`). Mix = the method of each buyer's first
payment information, as the loadgen pays (`../../timing/calibration/scripts/loadgen.py:287`). The generator's default:
the original model's seed (INVOICE 0.445, PREPAYMENT 0.416, CREDIT_CARD 0.139); `--payment-mix-from STATE` takes it
from a seed `state.json` (`../../timing/calibration/results-kotlin/seed/state.json`; the mix `misarch-kotlin.m` was
generated with is in its header).

| Step | Original | Kotlin (default mix) | Rule |
|---|---|---|---|
| `startPayment → createShipments`, `→ setInFulfillment` | 1 | 0.584 | INVOICE + CREDIT_CARD |
| `startPayment → updatePaymentStatus` (callbacks) | 1 | 1.0073 | 1 + CC·(f + f² + f³), f = 0.05: credit-card retries (they reach `payment/register`, `:177-191`) |
| `updatePaymentStatus → createShipments`, `→ setInFulfillment` | – | 0.3923 | PREPAYMENT·s / callbacks |
| `updatePaymentStatus → releaseReservation` (T26) | 0.02 assumed | 0.0207 | (PREPAYMENT·f + CC·f⁴) / callbacks: a FAILED prepayment callback publishes payment-failed (fix P5); the 4th credit-card failure |

Per placed order this gives createShipments 0.98 × 0.9785 (original: 0.98).

**Same structure, working in Kotlin.** These rows are in the original model too (from the wiring), but the
original's handlers failed at run time; on the Kotlin stack the calibration measures their work.

- `createInvoice` with its User, UserAddress, VendorAddress and Order copies. Invoice consumes T23 and
  T2 (route served), T3/T4 and T5 (stored with all fields), and creates exactly one invoice per order
  (`invoice service/InvoiceService.kt:95-138`).

- `createOrder`'s S23 result (shipment fees) is part of the order amount (`order service/OrderService.kt:61,125`).
  The need is non-strong (fees do not need current data).
- T9 is acknowledged by order (the original answered 422). The address check in createOrder uses the
  UserAddress copy (`:84-92`).
- Not in Kotlin, and not modelled: the original's redelivery loops (invoice, order visibility, discount validation,
  duplicate replica events).

**Checked, as in the original:** all T2/T3/T5/T6/T8/T11–T14/T17/T19/T21/T23/T24/T29/T31/T32/T34 subscriptions,
S20–S23 in code order (`order remote/RemoteServices.kt:46,81,109,139`), the 6 gateway joins (same SDL), the provider

**Not modelled:**

- The discount-validation failure rate is an assumption (2 %, as in the original model). A Kotlin integration run

## 2. Copies fed by processes

return, payment, invoice and shipment hold Order copies (T19/T23/T25 payloads). The Order copies of payment, invoice
and shipment are `carriedByProcess` (no replication on an Order write), return's is `fedBy` placeOrder. The same
mechanism feeds order's ProductVariant copy by updateProductVariant only, the five T8 copies by
createProduct/createProductVariant, and the User copies by createUser only (updateUser publishes nothing). Evidence
in `misarch-kotlin.m` (need comments). With these, createOrder sends no broker message and placeOrder 11.76, and the
publishes/messages of adminNewPrice 1/3, adminCreateVariant 2/8, adminCreateProduct 3/10 and eventUserCreate 2/10
match the code.

Visits per placeOrder: reserveItems 1, validateOrder 1, startPayment and createInvoice 0.98, updatePaymentStatus
0.987, createShipments/setInFulfillment/markShipped/markDelivered 0.96, releaseReservation 0.040,
createOrderCompensation 0.001. createProductVariantVersion has 1 publish and 3 deliveries.

The `createReview → Product` copy is read only by review's `_entities(Product)`, not by createReview; the model
keeps the original model's consumer convention.

## 3. Calibration

The demands are msa's calibration mapping (`calibrate.py`, not in this package) of the Kotlin isolation demands
(`../../timing/calibration/results-kotlin/demands.json`), the same mapping as for the original stack. The Kotlin request
paths enter only through the seed's visits: `createInvoice` and the callback steps in the placeOrder chain, return as
a copy holder in adminNewPrice/adminCreateVariant/adminCreateProduct, and invoice as a working User copy holder in
eventUserCreate. An operation run fewer than 0.01 times per request is not measured by that request (`MIN_VISITS`;
otherwise `createOrderCompensation` would inherit placeOrder's scale). The payment mix and the 2 % validation
failures are inputs.
